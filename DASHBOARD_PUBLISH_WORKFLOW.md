# Dashboard-Thuno display publication workflow

Scope: `Khaduyadv/Dashboard-thuno`, branch `main` only. This workflow publishes display content; it does not run `/Cong no`, issue a certificate, alter Source of Truth, or authorize AIOS consumption.

1. **Pin read-only inputs.** Record exact SHA-256, effective date, row count, and source lineage for the current Actual certificate/artifact, MD/Export references, Staff Assignment, and Staff Input Plan. Do not use a stale root copy when a run-bound source is available.
2. **Build display layers independently.** Keep certified Actual artifact and certificate byte-for-byte unchanged. Keep the raw Staff Plan payload unchanged. Assignment-remapped Actual and plan comparisons are derived display layers, explicitly not certificate claims. Keep plan owner from the input separate from currently assigned CSKH.
3. **Reconcile before release.** Verify certified Actual totals; derived shop sum must tie exactly while remaining separately labelled. Verify all Assignment keys are unique and complete, source effective date is proven, and plan installment count/amount and match/mismatch totals reconcile. Preserve duplicate-group and freshness warnings. Exclude contacts, customer notes, credentials, and raw source events.
4. **Create a composite manifest.** Bind each source and display-layer SHA separately, run ID, certificate, Assignment effective date, plan freshness, totals, and publication predecessor. Never claim that a composite HTML hash is the Actual certificate hash.
5. **Validate locally.** Check JSON schemas, embedded SHA checks, filters, hierarchy and Shop drill-down. Confirm no source payload or certified artifact changed. Review the exact changed-file list and ensure only Dashboard-Thuno display files/manifest/workflow documentation are included.
6. **Publish without rewriting history.** Re-read `main` immediately before commit. Commit only if it is still the expected predecessor; use a normal fast-forward update, never force-push. If the predecessor moved, stop and reconcile against the new head rather than overwrite it.
7. **Read back.** Fetch the committed raw files and verify their hashes, then verify GitHub Pages entrypoint and the Actual, Assignment-derived view, Staff Plan, totals, freshness notices, filters, and Shop drill-down. Retry Pages readback only within a bounded interval. Record commit SHA and publication receipt.
8. **Replay and recovery.** If the same content/run is already live, verify readback and make no new commit. If publication fails after commit status is uncertain, inspect `main` before any retry. Recover with a new forward commit; do not rewrite history. A display publication never substitutes for Production certification or governance approval.
